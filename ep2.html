認証と認可は別物

一番よく混ざるところ

認証 ＝ あなたは誰？

本物の「あなた」かどうかを確かめる。ログインがこれ。

受付で身分証を見せる
401失敗すると「あなた誰？」
入館証がない・期限切れ・偽物
VS

認可 ＝ あなたは何をしていい？

誰かは分かった上で、そのデータや操作が許されているかを確かめる。

社員証で入れる部屋が決まっている
403失敗すると「あなたは通せません」
本人だけど、そこは権限外
🚨 よくある事故：認可チェックの漏れ
GET /api/orders/123 自分の注文 → GET /api/orders/124 に書き換えたら他人の注文が見えた

ログイン（認証）はちゃんとしているのに、「その注文はあなたのもの？」（認可）を確かめていないと起きる。WAFも素通りする（攻撃っぽくない、普通のリクエストだから）。画面でボタンを隠しても、APIを直接叩かれたら意味がない。認可は必ずサーバー側で。

入館証（JWT）の中身

原則1「偽造させない」の正体
eyJhbGciOiJSUzI1NiJ9.eyJzdWIiOiJ1c2VyLTEyMyIsImV4cCI6MTc2....SflKxwRJSMeKKF2QT4fwpMeJf36POk6y...
ヘッダー

署名のやり方（アルゴリズム）

中身（ペイロード）
{
  "sub": "user-123",     ← 誰か
  "email": "taro@example.com",
  "exp": 1763456789      ← 有効期限
}
署名

役所だけが持つ鍵で押したハンコ。中身を1文字でも書き換えると合わなくなる

⚠️ 中身は誰でも読める

暗号化ではなく、ただの変換（Base64URL）。だからパスワードや個人の秘密を入れてはいけない。

✅ でも書き換えはできない

守っているのは「隠すこと」ではなく署名。「user-123」を「user-124」に書き換えると、ハンコが合わなくなって弾かれる。

APIキーとトークンの違い

🔑 APIキー ＝ 合鍵

  • 誰が使っているかは分からない（持っている人＝使える人）
  • 基本、自分で無効にするまでずっと使える
  • 漏れたら、気づくまで使われ放題
  • 仕組みが簡単。サーバー同士の通信や外部サービスの利用向き
ポストに隠した合鍵
VS

🎫 トークン ＝ 名前と期限つきの入館証

  • 誰の入館証か書いてある
  • 期限が短い（数分〜1時間など）
  • 盗まれても、すぐ使えなくなる（原則3）
  • 仕組みが少し複雑。ユーザーのログイン向き
名前入り・当日限りの入館証

💡 ブラウザで動くJSにAPIキーを書くと、DevToolsで誰でも見られる。フロントに置いた時点で「隠せていない」。

入館証をブラウザのどこに置く？

localStorage と Cookie の違い
🗄️
localStorage

机の引き出し

JSで出し入れする保管場所。APIを叩くときに、自分で取り出してヘッダーに付ける。

  • 勝手には送られない（なりすまし送信が起きにくい）
  • 別ドメインのAPIにも付けやすい
  • JSから読める＝部屋に入った泥棒（XSS）に中身を持ち出される
🪪
Cookie（HttpOnly / Secure / SameSite）

首から下げた入館証

ブラウザが、そのドメインへのリクエストに自動で付けて送ってくれる。

  • HttpOnlyならJSから読めない＝中身を持ち出されにくい
  • 自動で送られる＝偽サイト経由で勝手にかざされる（CSRF）ので対策が必要
  • 基本は同じドメイン向け
🧠
メモリ（JSの変数）

手に握っておく

保存せず、画面を開いている間だけ持っておく。

  • 保存されないので、一番持ち出されにくい
  • リロードやタブを閉じると消える

→ よく「更新用トークンはHttpOnly Cookie、本命のトークンはメモリ」と組み合わせる

ひと目で比べる

localStorageCookie（HttpOnly）
JSから読める？読める読めない
自動で送られる？送られない（自分で付ける）送られる
一番気にする攻撃XSS（スクリプトを仕込まれて盗まれる）CSRF（偽サイトから勝手に送られる）
主な対策XSSを作らない、トークンの期限を短くSameSite属性、CSRFトークン
向いている構成APIが別ドメイン、社内ツールなど画面とAPIが同じドメイン（Ep1の「CDNでまとめる」構成）
SameSite＝「うちの建物のゲートでしかピッと反応しない入館証」
⚠️ どっちを選んでも、XSSがあれば負け

Cookieは中身を盗まれにくいだけで、XSSがあれば「その場で本人として操作される」ことは防げない。本当の対策はXSSを作らないこと（入力値をそのままHTMLに埋め込まない、など）。

✅ 迷ったときの目安

一般向けで、画面とAPIが同じドメイン → HttpOnly Cookie。
別ドメインのAPIや社内ツール → localStorage＋短い期限でも可。
大事なのは「なぜそこに置いたか」を説明できること。

AIが平気でやってくる「やっちゃダメ集」

レビューでここに気づければ合格
原則2
鍵をコードに直書き

そのままGitHubにpushすると、公開リポジトリなら数分で拾われて悪用されることもある。

→ シークレット管理（Secrets Manager / Parameter Store など）や環境変数から読む
原則2
フロントにAPIキー

ブラウザに届いたものは全部見られる。

→ キーが必要な処理はサーバー側でやる
原則2
ログにトークンを出力

ログを見られる人全員が「あなた」になれる。

→ トークンやパスワードはログに出さない（マスクする）
原則3
有効期限がやたら長い

「面倒だから期限30日」は、盗まれたら30日使われ放題。

→ 期限は短く。更新用のトークン（リフレッシュトークン）で延長する
原則3
権限が全部入り

とりあえず管理者権限、IAMで「*」（何でもOK）。

→ 必要な分だけ（最小権限）
認可
チェックが画面側だけ

ボタンを隠しても、APIを直接叩けば通る。

→ 認可は必ずサーバー側で
